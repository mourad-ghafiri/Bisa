# Feature status

What the platform does today, what is partial, and what it does not do — stated so nobody has to
rediscover it. Everything here describes the code at `HEAD`. A row leaves this page when the code
lands; nothing here is a schedule.

Three levels are used throughout:

| Level | Meaning |
|---|---|
| **Implemented** | built, wired end to end, and covered by tests |
| **Partial** | the surface exists and works, with a named limit |
| **Not implemented** | absent; what stands in is named beside it |

---

## Implemented

### The crates

| Crate | What it does |
|---|---|
| `bisa-core` | the zero-I/O domain: ids, the workflow definition and its validation, the run machine, work items, projects, channels, agents and teams, the GEP kind registry, settings, capabilities, errors — every rule a pure function with a unit test |
| `bisa-store` | the filesystem as truth: signed journals, snapshots and JSON records, with a rebuildable SQLite index; the catalog, identity, the inbox, recall |
| `bisa-engine` | the orchestrator: every workspace mutation through one typed facade and one event bus — the executor, scheduler, gates, waits, listening for events, code host, IDE effects, language servers, models, presence |
| `bisa-node` | the axum daemon over the engine: HTTP/JSON on a unix socket (`0600`) with optional loopback TCP behind a bearer token, one SSE stream at `/events` |
| `bisa-cli` | the `bisa` multicall binary — the CLI, the `node` daemon and the `mcp` server in one executable |
| `bisa-collab` | the collaboration wire: the gift-wrap envelope, the control messages, the invite code, the relay pool with per-relay health and, for a relay that was tried and is not connected, why; the wire's one TLS crypto provider (`ring`), installed where a client is made — every real relay is `wss://`, and with both of rustls' backends compiled in a client built without one panics |
| `bisa-guest` | a hosted member's replica of a workspace on another node, and the session that speaks for them — the crate a mobile client embeds |
| `bisa-net` | the host's pump: what a workspace says to the people it hosts, pairwise over relays by what each role reaches; the direct QUIC transport |
| `bisa-mcp` | the MCP server injected into every harness session; the tool set differs by scope and the General Agent and the Workflow Agent get more; the common set every session holds carries an agent's memory across sessions — `recall_store`, `recall_get`, `recall_list` |
| `bisa-harness` | the harness contract: the adapter and session traits, the event vocabulary, the three-tier catalog, subprocess plumbing |
| `bisa-adapters` | the shipped adapters: Claude Code, Codex, ACP (Goose, Cursor Agent, `omp acp`, `opencode acp` and any other ACP speaker), pi-rpc, omp, OpenCode, GitHub Copilot CLI, Grok Build and Gemini CLI (each an id of its own over the one ACP module — found by a probe that reads a version, its model and its effort set as session config options, the model first — Gemini CLI's model the draft's way, `session/set_model`, and no effort, since it has no control for one; a model a session does not offer passed over for the plan's next; never started with a word that allows a tool unasked), custom JSON, A2A |
| `bisa-codehost` | pull requests, checks, reviews, review threads — read, resolved, replied on — merges and branch deletion behind one capability-driven `CodeHost` trait — GitHub, GitLab and Bitbucket, each the machine's own CLI (`gh`, `glab`) first and the host's API second, the CLI asked through a port with a scripted fake for tests — and an in-memory fake code host |
| `bisa-lsp` | supervised, proxied language servers: the JSON-RPC codec, a preset catalog, root-relative URIs |
| `bisa-vcs` | the git layer: typed, time-boxed, argv-only subprocess calls in two tiers — a safe tier and a consented tier that writes a recovery ref before anything moves; it cannot revert a file |
| `bisa-iso` | work-item isolation behind one trait: a git worktree and a plain copy |
| `bisa-cache` | the TTL cache toolkit — a cell and a keyed cache with hit/miss stats and a clearable registry |
| `bisa-http` | the one HTTP client set — a proxy policy (the environment\'s, none, or a manual pair with a bypass) over swappable `reqwest` clients every network-reaching crate shares, and the environment a child is handed to obey it |
| `bisa-log` | the diagnostic log — one `tracing` subscriber per process, a JSON-lines file per process family in a folder of its own under the workspace's `logs/`, rotated by the hour or the day and pruned by count, the level retuned live from the `logging.*` settings; a flight recorder of the last lines at `debug` and above; a crash report for every death — a panic with its backtrace, a run that ended without a goodbye found by the next start from its run marker, the desktop's node exiting with its last stderr lines; errors only by default; shared with the desktop shell by path; nothing is sent anywhere |
| `bisa-connectors` | outside platforms' HTTP APIs behind one declarative shape — request building, the four body kinds, the six auth schemes and OAuth2 with PKCE, the host allowlist, a capped retry, the circuit breaker, a write's idempotency key — behind traits the engine implements |
| `bisa-decision` | the Decision-Making Agent's providers behind one port — Jev, RLCD, a prompted harness or agent, a scripted fake — with the typed question, the answer and the failure kinds the node maps to statuses |
| `bisa-security` | the Redactor, the Tool & Commands Guard and the Classifier's contract — pure rules over text, the placeholder vault; no I/O |
| `bisa-ssh` | `ssh`, `ssh-keygen` and `ssh-add` for git hosts as typed, time-boxed, argv-only subprocess calls — public keys and their fingerprints, what ssh-agent holds, what `ssh -G` would offer, a host's greeting; a private key is never opened |
| `bisa-mobile-development` | the mobile toolchain and the devices on this machine as typed, time-boxed, argv-only subprocess calls — Flutter, Xcode, the iOS runtimes, CocoaPods, the Android SDK and Java probed; simulators and emulators listed, booted, shown, made and captured; `flutter run` never spawned |
| `bisa-mcp-probe` | the client that dials an installed MCP server — stdio, Streamable HTTP, the older HTTP+SSE — in either protocol era and reports what answered; it never runs a tool |
| `bisa-netrules` | the one grammar of a host pattern (`host[:port]`, `*.suffix`), the loopback names and the headers a connector definition may never set — pure, shared by the domain, the connectors client and the security rules |
| `bisa-i18n` | the catalog and its rendering — every message the platform says to a person, in Fluent under `locales/<lang>/`, compiled in; a locale negotiated from the environment or an `Accept-Language`; a `Text` rendered at the edge that talks to the person; the migration's ratchet |

| An OAuth app or device flow of the platform's own | **Authenticate** in Settings › Git & code hosts runs the host CLI's own browser sign-in (`gh auth login --web`, `glab auth login`) in a terminal tab, and the credential lands where the CLI keeps it; a token pasted into the panel is the other door, and the only one for Bitbucket Cloud |
| Bitbucket Server, or a CLI for Bitbucket | Bitbucket Cloud over its API with a token; a self-hosted remote told `codehost.kind = bitbucket` is refused by name in the Connection card |
| Switching `gh` between accounts on a GitHub Enterprise host | `--hostname` binds the instance; the bound login is asked of `gh auth token --user`, and a login `gh` does not hold falls back to a stored token |
| A passphrase set on a key from the platform | `ssh-keygen -p` in a terminal — a passphrase on argv would be visible to every process; the SSH keys panel says so |
| Writing `~/.ssh/config` for you | *Copy a Host block…* in the SSH keys panel offers the text; you paste it. A key is bound to an organization through the profile's `core.sshCommand`, a file the platform owns |
| A `GIT_SSH_COMMAND` read from your terminal's environment | only the node's own environment is reported (the Connection card's *overridden* note) |
| An SSH key for a server, or a host that is not a git host | the SSH keys panel is for git hosts alone |
| A diff of a synced workstream script against the text you approved | the whole text, read and approved as one under About › Settings › Workstream scripts |
| Shared rebuildable directories across a project's workstreams | the post-create script (`npm install` per checkout) |

### Agents and models

| Gap | What stands in |
|---|---|
| An effort on Goose, Cursor Agent, an A2A agent or a custom harness: none documents a control the platform can set | the harness's own default; a step that pins an effort on one of them alone is refused when saved |
| A model or an effort for a harness a person opens in a terminal | the harness's own `/model` and effort commands — the session is the person's |
| Account usage for GitHub Copilot CLI, Grok Build and Gemini CLI: none documents a source for what the account has left (`grok usage` is one session's tokens; Gemini's quota page states each tier's daily requests and nothing reads what is left of them) | the footer and Settings › Harnesses say *unsupported* in the harness's own name; Copilot's `/usage`, Grok's own status line and Gemini's `/stats model`, in the harness |
| A model of an ACP agent whose session offers no `model` option: the agent cannot be told | the agent's own default — nothing is sent, as before; an agent that does offer the option is set, or the launch walks the plan |
| A judged effort kept across a node restart, or changed in the middle of a live session | the next launch asks again; a conversation keeps the effort its first message was given |
| The levels of a model the platform does not know, read from the harness at run time | the levels every model of that harness takes; pi and an ACP agent fit the level themselves |
| The platform's own tools on pi, oh-my-pi and a custom harness: their adapters hand a session no MCP servers (`HarnessCaps::MCP_SERVERS` is Claude Code's, Codex's, OpenCode's, GitHub Copilot CLI's, Grok Build's, Gemini CLI's and an ACP agent's) | a conversation, which is answered in words; a workflow's `agent` step yields through the platform's tools, so it is placed on a harness that takes them |

### Workflows

| Gap | What stands in |
|---|---|
| A generic `http` connector over any host: a definition must declare its hosts, and a bare `*` is refused | a custom connector that names its own host |
| Inbound events from a platform — a Slack event, a Gmail push — verified with the platform's own signature scheme | a public `hook` start (`POST /hooks/{host}/{step}`, the start's secret as a token or a GitHub-compatible HMAC), or a `connector` start that polls |
| A pull request somebody opens on the code host itself as a `project` event: the platform sees the pull requests its own workstreams opened or adopted | a public `hook` start the code host calls |
| Retention of a standing goal's, or a listening workflow's, finished runs: every run's folder stays | a goal's own list keeps its queued runs and its newest fifty; the index and the folders keep every one |
| A place and an author on a boundary event's post, from the designer's form: both are kept as written | the definition's `scope` and `author` in a file, or a `notify` step on a path the boundary diverts to |
| A picker for a `platform` start's topic: the field is free text | validation refuses a topic the runtime does not say (`unknown_topic`); the list is in the [events guide](guide/events.md#platform) |
| A bundled OAuth client for Google, X or TikTok | the person registers their own client at the platform and enters its id and secret on the account |
| A default value on a connector operation's parameter | the parameter's `doc` says the usual value; the step fills it |
| Keymap commands for the canvas's own keys: the keymap's `designer` scope holds the four panel commands, and the canvas's keys act on the focused canvas only, outside the keymap and its reference | `Delete`, `⌘D`, `⌘Z`, `⌘⇧Z`, `Esc` on the canvas |
| Workflows in the omnibox or the workspace store: the library fetches on visit | `#/workflows` |
| A diff between two revisions of a workflow, or of a run's amendments | the journal's `amended` facts and the run's frozen copy |
| The designer under `node --test`: the forms, the hooks and the tab components have no React-level tests | `workflowLayout`, `workflowGraph` (renames, on-fail routes), `runView`, `stepKinds` and `designerSession` tests cover its facts |
| Changing a step's kind in place | delete the step and add one of the other kind; flows are redrawn |
| A `notify` scope naming a goal or a workstream from the form | a channel, the goal's own conversation, or a text input the person fills at start |
| A calendar picker for a `wait` on a `schedule` | a cron expression and a zone in a text field |
| Model-pin validation against a harness whose model list the engine has not cached | `UnknownModel` fires once the list is known; an unavailable pin fails the step at launch |
| Harness-name checks in an offline `bisa workflow validate` | the same command against a running daemon |
| A typed `400` (a `code`) for an unknown key in a `POST /goals/{id}/run` body — the node answers `400` with the extractor's sentence in `error` | send `{}`, `{inputs}` or `{inputs, start, event}` |
| A field-by-field merge of a designer conflict | keep mine or take theirs, and undo after *Take theirs* |
| Asking before a derived slug is suffixed on collision | `disambiguate` |
| A `check` step running in a project when the goal has several | name a project on the agent steps |
| A stored design state (proposed, declined, adopted) — it is inferred from the open gate and the run; a declined adoption is a journal note | the *Designed for this goal* banner reads `pending_gates` and `run` |
| A record of a project's creation mode (new, clone, import, adopt, an agent's `create_project`) | `ProjectRoot` and `ProjectOrigin` |
| Verification of a peer's project or workflow origin against the run it names | provenance is a claim signed by its author, as for `GoalOrigin` |
| A step's *name* on a step-born project's record — only its id | the About tab prints the step id |
| Loop-edge detection independent of display order, in a definition with no `start` step whose first step is a loop's target | give it a `start` step — a definition with one begins there, whatever the order |
| A one-shot `bisa design <goal>` without a daemon | start the node, or pick a workflow with `workflow use` |
