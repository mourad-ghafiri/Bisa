# Documentation

The documentation set under `docs/` describes the platform as built, in the present tense, at
`HEAD`. Three kinds of page are kept apart on purpose: a **guide** teaches one thing end to end to a
person using Bisa, a **reference** enumerates and is looked up, and **architecture** explains how the
system is shaped and why each rule holds. Four reference pages are generated from the code; the rest
are held to the code by guard tests that run with the workspace's tests.

## Where it lives

- `docs/guide/` · `docs/reference/` · `docs/architecture/` (with `docs/architecture/crates/` and `docs/architecture/ide/`) · `docs/contributing/` — the four folders; [docs/README.md](../../README.md) is the index.
- `docs/feature-status.md` — what is implemented, partial and not implemented; `docs/contributing/coverage.md` — the suites behind every implemented feature.
- `docs/reference/http-api.md` · `docs/reference/settings-keys.md` · `docs/reference/catalog.md` · `docs/reference/keymap.md` — generated by `just gen-api-docs`, `just gen-settings-docs`, `just gen-catalog-docs` and `just gen-keymap-docs`; never edited by hand.
- `crates/bisa-core/tests/it/docs.rs` — the set's guard.
- `scripts/check-mermaid.mjs` — every Mermaid block parses with the Mermaid the desktop renders with.
- `scripts/lint-terminology` — the vocabulary, over the whole tree.
- The two READMEs the set routes from — the repository's [README.md](../../../README.md) and [desktop/README.md](../../../desktop/README.md) — are held by the same guard.

## Rules a change must keep

- Every relative link resolves, and an anchor in a link is a heading of its target as a renderer makes it: lowercase, spaces become hyphens, every character that is not a letter, a digit, a hyphen or an underscore dropped (`crates/bisa-core/tests/it/docs.rs`).
- A code span that names a path in the repository names one that exists; write the full path.
- A settings key quoted in a code span is registered: a dotted word that starts with a settings group and is neither a key, an engine topic, a decision point nor an addon bridge word fails.
- Every crate page names every source file of its crate as a code span.
- The set speaks as built, never as a plan: the guard refuses the planning voice and phase tokens.
- The vocabulary is lint-enforced: a retired word fails `scripts/lint-terminology`; the article after a renamed noun is a reviewer's to catch ([Terminology](../terminology.md)).
- A generated page is regenerated in the same change, never edited; CI diffs all four ([Release § Generated files travel with the change](../release.md#generated-files-travel-with-the-change)).
- Every Mermaid block parses (`just check-mermaid`); every implemented feature on the status page has a row on the coverage page.
- Other guards hold one page each to its code: the MCP tools page to the server (`crates/bisa-mcp/tests/it/docs.rs`), the CLI page to the parser (`crates/bisa-cli/tests/it/docs.rs`), the topics and the engine page to the engine (`crates/bisa-engine/tests/it/docs.rs`), the index schema to the store (`crates/bisa-store/tests/it/schema_doc.rs`), the keymap list to the model (`desktop/src/shell/keymapDocs.test.mjs`), the addon API to the bridge (`desktop/src/scenarios/addons.test.mjs`).

## Testing a change

- `scripts/test module core docs` — links, anchors, code-span paths, settings keys, crate pages, the planning voice, coverage rows.
- When the page you changed is one they hold: `scripts/test module mcp docs`, `scripts/test module cli docs`, `scripts/test module engine docs`, `scripts/test module store schema_doc`, `scripts/test module node routes`.
- `scripts/lint-terminology docs` and `just check-mermaid`.
- `just check-api-docs`, `just check-settings-docs`, `just check-catalog-docs`, `just check-keymap-docs` — the generated pages are current.
- `just verify` once, at the end ([Testing rules § Running](../testing-rules.md#running)).

## Common changes

- [Regenerate and verify](../recipes.md#22-regenerate-and-verify) — after a route, a key, a catalog entry or a command changed.
- Every recipe ends at the pages it touches — [Add an engine event](../recipes.md#4-add-an-engine-event) a sentence on the engine page, [Add a workspace path](../recipes.md#10-add-a-workspace-path) the layout page, [Change the index schema](../recipes.md#11-change-the-index-schema) the schema block.
- A third-party identifier that spells a retired word is excused in place, with a reason ([Terminology § The lint](../terminology.md#the-lint)).
- `CHANGELOG.md` gets its line under *Unreleased* in the right kind ([Release § The version and the changelog](../release.md#the-version-and-the-changelog)).

## Compatibility

- The reference pages describe the public contract: [Compatibility](../../reference/compatibility.md) names, surface by surface, the page that is its reference. A deprecation is marked on its reference page and under *Deprecated* in the changelog ([Deprecation](../../reference/compatibility.md#deprecation)).
- A change to the documentation alone is *no contract change*; a page that documents a new interface goes with the change that adds it ([Keeping compatibility](../compatibility.md)).

## Review focus

- Present tense, the code at `HEAD`; a page says what is built, and what is not is on the feature-status page ([Docs and language](../review/docs-and-language.md)).
- The right kind of page: a guide does not enumerate, a reference does not teach, architecture says why.
- Facts checked against the code; a generated page regenerated, not edited ([Code review](../review/code.md)).
- One word per concept, and plain, precise sentences.
