# Testing rules

The platform runs unattended agents next to people's repositories, so its own tests are held to the
rule it holds the product to: **nothing in a test can make a change unrecoverable.**

## What a test may never do

No test, fixture, helper, bench or CI step contains `rm`, `rm -rf`, `remove_dir_all`, `DROP `,
`git clean`, `--force`, or a write outside a temporary directory. A fixture is a `tempfile::TempDir`
and is dropped, never deleted by hand. Git tests use temporary repositories with a **local bare
`origin`**, so a push in a test leaves nothing but the machine it ran on.
`crates/bisa-core/tests/it/layering.rs` greps every test source in the workspace for those
tokens — spawning `rm`, `rm -rf`, `DROP TABLE`, `git clean`, a plain force push, `remove_dir_all`,
the reset script — so the next one fails `cargo test` rather than somebody's afternoon. The
production spelling `--force-with-lease` may be asserted on; the rule's own table is exempt.

A destructive-operation test asserts on **typed errors and recovery refs**, never by destroying a
fixture and checking that it is gone.

## Where a test lives

A rule in `bisa-core` gets a unit test beside it. A behaviour that crosses a boundary — the
store on a real directory, the engine on a real store, the node over its socket — gets an
integration test in that crate's **one integration binary**: `tests/it/main.rs` declares a module
per topic (`tests/it/guided.rs`, `tests/it/routes.rs`), and shared fixtures sit beside them
(`tests/it/common/`, `tests/it/support/`) as `use crate::common;`. One binary rather than one
per file because Cargo compiles and links every `tests/*.rs` as its own crate: the engine's
twenty-six files were twenty-six link steps and twenty-six copies of the dependency graph on disk,
and `cargo check --tests` paid for all of them. A module is still runnable alone —
`scripts/test module engine guided` filters the binary by the module's name — so nothing is lost
but the wait. A fact the desktop computes lives in a pure `.mjs` module
with a `.d.mts` beside it and a `.test.mjs` run by `node --test`; **there is no jsdom** and there
should not be — a wrong pixel is visible, a wrong fact is not. A **scenario** — a person's journey
that crosses several models — lives under `desktop/src/scenarios/`, one `.test.mjs` per journey: it
steps the reducers the way the components do, asserts after each step the facts the screen would
show, and round-trips through serialize and restore wherever state persists. It is a model test
with a storyline, not a component test: no DOM, no render.

A **journey** is the platform from end to end with no window: the real `bisa` binary, the real
node over its socket, the real MCP server, and agents that are scripted. It lives in the command
line crate's integration binary, `crates/bisa-cli/tests/it/e2e/`, one file per journey, named
after what it proves — that crate is the one that builds `bisa`, so Cargo hands its tests the
binary's path. A journey asserts what a feature promises a person — what the inbox asks, what a
run came to, what is on disk once the daemon is gone — never how the code keeps it.

| Piece | What it is |
|---|---|
| the **sealed workspace** (`e2e/sealed.rs`) | every process a journey starts has its environment **cleared and built again from a short list**: a home and a temporary folder of the journey's own, a `PATH` of the scripted agent's folder and `/usr/bin:/bin`, `SHELL=/bin/sh`, git isolated (`GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`), `--file-keys`; the coverage tool's variables are the only ones kept. No token, no proxy, no agent socket, no real harness and no code host CLI is in reach. `harness.usage.reads` and `sync.iroh.enabled` are turned off before the first start, and `sync.enabled` is off by default, so nothing is dialled |
| the **scripted agent** (`tests/scripted_agent.rs`, the package's second binary) | a harness that does what a script says. It speaks the Agent Client Protocol, and is placed under the name of an ACP target the platform already knows (`goose`) — or of a harness with an id of its own (`copilot`, `grok`, `gemini`: `Sealed::install_agent_as`), where it answers the adapter's `--version` probe with a version — so the daemon finds it by the adapter's own probe and launches it as it would a person's harness — **no product code knows a test exists**. A script that names `models` makes its sessions choose their model, as an agent with a `model` config option does. It starts the MCP servers it was handed as a harness does — the command, the arguments, the environment — asks each for its tools (`tools/list`, kept with the fact that the server started) and calls them. Its script is `<binary>.script.json`: per turn, the scope it fits (`goal`, `work_item`, `conversation`), words to say, tools to call — or the word `"every"`: every tool the platform's server lists, each with nothing in its hands —, files to write in its own folder, a question to ask first, a turn to hold until it is cancelled. What it was told is `<binary>.record.jsonl`, a fact a line |
| the **daemon** | the journey's own child. It is asked to stop as a supervisor asks (`SIGTERM`): it must end well and leave no socket. A crash is staged by ending it where it stands. A daemon that cannot bind its socket **fails the journey in its own words** — a skip is not a pass. The fixture ends a daemon still up when it is dropped, so a journey that failed leaves no process behind |

A journey never asks for the Trash, a sign-in, the SSH routes, a harness's usage, or a push beyond
a local bare repository; a script never spells a destructive command, even as data — the guard
over test sources reads every file under `tests/`. The journeys run as one nextest group
(`journeys` in `.config/nextest.toml`), two at a time, with a longer window:
`scripts/test module cli e2e`. The shipping build names its binary (`--bin bisa`), so the scripted
agent is never built for a release nor copied into a bundle.

## Running

**One module at a time.** The whole workspace takes the better part of an hour and hides which
module is slow or wrong; a module answers in seconds and names the culprit. `scripts/test` (and the
matching `just` recipes) narrows every form and sets `GIT_CONFIG_GLOBAL=/dev/null
GIT_CONFIG_NOSYSTEM=1`, so no fixture repository sees this machine's git config:

| Want | Command |
|---|---|
| one crate's unit tests, one module of them | `scripts/test lib engine` · `scripts/test lib core run::` |
| one integration binary, one test of it | `scripts/test module engine guided` · `scripts/test module engine projects publish` |
| the journeys through the binary | `scripts/test module cli e2e` |
| a suite behind a cargo feature — not built without it, so a filter that matches none of it says *no tests to run* | `FEATURES=a2a scripts/test module node a2a` · `FEATURES=a2a scripts/test crate adapters a2a` · `FEATURES=iroh scripts/test module net iroh_e2e` |
| one crate, everything | `scripts/test crate store` |
| the Rust half — the workspace, then the Tauri shell | `scripts/test rust` (`just test-rust`; `verify` runs it, then the desktop once under its coverage gate) |
| what uncommitted changes touched | `scripts/test changed` |
| one desktop directory, or one file | `scripts/test desktop views/_workbench` · `cd desktop && node --test src/views/_work/prFormModel.test.mjs` |
| the desktop's scenarios | `scripts/test desktop scenarios` |
| the Tauri shell | `scripts/test tauri` |
| line coverage, measured and judged · one half · one crate's suites with its file list · the baselines raised | `just coverage` · `just coverage-of desktop` · `just coverage-crate engine` · `just coverage-write` |

Which suites prove which feature — crate by crate and screen by screen — is one page,
[Feature coverage](coverage.md), held to the feature-status page by a guard.

The whole-workspace forms (`cargo test --workspace`, `cd desktop && npm test`, `just verify`) are
the gate at the **end** of a crate's hardening pass, never the loop. Every tree carries a
line-coverage ratchet — `just coverage` (in `just verify`) measures the workspace, the shell and
the desktop's models and holds each crate and each desktop directory to the figure in
`scripts/coverage/baseline.json`, which only rises ([Feature coverage § Line
coverage](coverage.md#line-coverage)); `just coverage-crate <crate>` is the loop, with the file
list and the bare lines. The desktop's models keep their quick floor too — `npm run test:coverage`
(`just desktop-coverage`) fails under 80 % of lines across `src/**/*.mjs`. A crate's pass ends when
every module of its one integration binary is green and its tree's figure has not fallen.

**A slow suite is a bug**, not a cost to wait out: a naked `sleep` becomes a poll with a deadline
(`common::until` / `wait_for`), a wall-clock wait becomes a config knob the test sets (engine tests
run with `events_enabled: false` and drive `tick_listeners_at` / `drain_signals` by hand, the clock
an argument; when the worker must run, `signal_poll_secs` goes to 1), and a suite that stays above a few
seconds is split or shares its fixture. Compile checks (`cargo check -p`, `cargo clippy -p
--all-targets`, `npm run build`) are cheap and run per crate.

## Faster builds

What the workspace sets, and why — each one is a measured lever, not a habit
([Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html),
[`--timings`](https://doc.rust-lang.org/cargo/reference/timings.html)):

| Lever | Where | What it buys |
|---|---|---|
| **One integration binary per crate** (`tests/it/`) | every crate | one link instead of one per file, one copy of the dependency graph on disk, `cargo check --tests` compiles each suite once |
| **Check the crate, not the workspace** | `just check <crate>` = `cargo check -p bisa-<crate> --tests` | seconds; the workspace-wide `--all-targets` check is `just lint`'s, once before handing over — it compiles every library twice (as a unit-test binary and as a dependency) plus benches |
| **Dependencies optimised, ours not** | `[profile.dev.package."*"] opt-level = 3`, workspace crates at 0 | tokio, hyper, sqlite and the crypto crates are compiled once and cached; a suite over them runs several times faster; the edit loop is unchanged |
| **Build scripts and proc macros optimised** | `[profile.dev.build-override] opt-level = 3` | aws-lc-sys, secp256k1-sys, blake3 and the bundled sqlite compile C in `build.rs`, which even `cargo check` must build and run |
| **Line tables, unpacked** | `debug = "line-tables-only"`, `split-debuginfo = "unpacked"`, `lto = "off"` | a panic still names its line; no `dsymutil` pass on macOS; no LTO pass on the optimised dependencies |
| **Symbols kept in release** | `[profile.release] strip = "debuginfo"` here and in the desktop shell | a crash report's backtrace names its frames in a shipped binary; only the debug info goes |
| **Two cores free** | `.cargo/config.toml` `[build] jobs = -2` | a check and a Vite build side by side no longer starve each other; a check alone loses a few percent |
| **rust-analyzer's own target directory** | `.vscode/settings.json` (`rust-analyzer.cargo.targetDir`) | the editor's check and the terminal's never lock each other's `Cargo.lock` or invalidate each other's cache |
| **tokio's features named** | the workspace dependency | `full` also pulled `io-std` and `parking_lot`; a crate that needs another names it |
| **One feature set per dependency** | `crates/bisa-deps/` (`bisa-deps`, generated by cargo-hakari from `.config/hakari.toml`) | `cargo check -p one-crate` never rebuilds tokio or hyper with a smaller feature set than the workspace check did — see `cargo hakari verify`. A test may dev-depend against the crates' own direction — `bisa-engine`'s tests on `bisa-mcp`, which depends on `bisa-core` alone — to drive a real client against a real socket; never the reverse of an existing edge |
| **nextest** | `just install-nextest`, `.config/nextest.toml` | every test in its own process, one pool for the whole run, a hung test ended at its timeout |

What is deliberately **not** set: a linker (Apple's current `ld` is the fastest on Apple Silicon;
mold is Linux-only and `-fuse-ld=lld` is not for this platform), the nightly parallel front end
(deadlocks are still open), and sccache (it cannot cache incremental workspace crates — the very
ones an edit rebuilds). Where the time goes is a question for `just timings`, whose report shows the
critical path and every stretch a compiler waited for a core. An edit to `bisa-core` rechecks
every crate downstream, comment or not — the fingerprint is the crate's metadata — which is one more
reason the root crate stays small and stable.

## A restart in a test

A restart is a second `Engine::start` (or `Node::start_in`) over the **same directory** after the
first is gone — **its keys included**: the fixture keeps them in files under the directory's own
`identity/` (`FileKeyStore`), as the product does. Keys kept in memory are minted anew by every
start: the second engine is then another owner, with no agent left to sign as. `Engine::shutdown()` is a clean handoff — the loops aborted, the socket unlinked — not
a crash, and a test may not pretend it is one: the crash is staged as the files a dead process
leaves — a run created straight in the store (`create_run` applies `Start` and runs no effect), a
session row still `live`, a question with no decision — and the second engine reads only those. The
dead session's child is a `sleep` the test spawns and ends itself, never a real harness and never a
process of the machine's. A new `StepKind` earns a row in `dies_with_the_process` and a case in the
interruption table (`crates/bisa-core/src/run.rs` — `StepInterrupted`), and the compiler
refuses the one that forgets.
