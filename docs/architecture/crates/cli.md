# bisa-cli

The `bisa` multicall binary, in three personalities: the command-line client, the daemon
(`bisa node`), and the MCP server a harness session is handed (`bisa mcp`). The CLI holds
no domain rule: it parses arguments, routes each command to a running daemon or embeds an engine
for one shot, and prints with one
output discipline.

## Entry points

`bisa <verb> …`. `bisa node [--listen <addr>]` runs the daemon; a non-loopback address
needs `--insecure-allow-remote`; a workspace an engine already holds — a node's, or a verb's that embedded one — is refused at the door (`EngineLock::holder`, before the workspace is opened), naming the holder's pid and the socket the node answers on, and the lock the engine takes stays the guarantee (I40). `bisa mcp --socket <engine socket> (--work-item <id> |
--goal <id> [--agent <id>] | --conversation <scope> --agent <id> | --note <id> --agent <id>)` is
the server the engine injects into every harness session — the engine spawns it, nobody runs it by
hand. Every verb is in [`docs/reference/cli.md`](../../reference/cli.md), and a test keeps that so.

## Errors

`anyhow::Result` at the top; a typed refusal from the store or the engine is printed as its own
sentence and exits non-zero — a `WorkflowInvalid` as its problems, one line per step. A
`Workstream::require_repository` refusal (a copy of a non-git project) is printed as the core states
it — the same sentence the node answers with.

## What this crate refuses to do

- hold a domain rule or a store write of its own — which way in a run is asked through is the
  core's reading (`WayIn::of`), a listener's view and a workflow's row the node's;
- start a run from an event in a command that embeds its engine: events are the node's;
- embed a second engine while a daemon holds the lock;
- pass `--force` or `--no-verify` to git; write global git config by any path but the engine's
  three named functions;
- take a token on the command line — `git account add` reads it from stdin;
- print a secret twice.
