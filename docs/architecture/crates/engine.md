# bisa-engine

The orchestrator — and **every filesystem effect**. The engine takes a store and a harness catalog
and runs the platform: every run event through one funnel and every run effect through one
interpreter, scheduling and placement, gates, waits, budgets, model failover, conversations,
listening for events, the two core agents' wakes, and the IDE's file, git, search and language-server effects.
It is the only crate that creates a directory for work, runs `git`, or launches a process; the node
calls it for every mutation ([07 — Layering](../07-layering.md), rule 2). `Engine` holds an
`Arc<Inner>`, the `EngineLock` that makes it the one engine on this workspace, and its task groups
(intake, conversation, collaboration, listening — the ear always, the event ticker and the signal
worker with `events_enabled` — and the wait ticker, a clock of its own). `warn_on_err` and
`debug_on_err` are the only sanctioned ways to drop a `Result`; the workspace lint denies `let _ =`
on a must-use value.

## What this crate refuses to do

- own transport: no HTTP, no SSE framing, no relay;
- parse a harness's prose outside the adapter boundary;
- discard a write — a journal or snapshot append is never dropped;
- record a gate decision, adopt a workflow or start a run from an agent's op;
- act on an event directly — every occurrence goes through the signal queue and starts a run under
  the same gates as human-started work; nor arm a listener nobody asked for: a person turns a
  workflow On, and an auto adoption arms only the starts nobody needs to see armed;
- write the person's global git config anywhere but its three named functions, open a private key,
  or write `~/.ssh/config` — a key is bound to an organization through the profile file the platform
  owns.

## The design ask

The question of a goal the Workflow Agent designs for is journaled under its stable subject `ask_human:<goal>` (`intake.rs::ask_human`), so the node rebuilds it after a restart; `ops::decide` and `decide_without_engine` resume the design on any Escalation of such a goal — an answer as given, a decision as words (`answer_or_verdict`) — and `check_adoption_inputs` binds an adoption's inputs before the gate is recorded, so a missing input is a 400 that leaves the adoption pending. `propose_workflow` and `start_run` withdraw the goal's `ask_human:` gates; `guided::schedule` records nothing for a phase that no longer applies; `note_proposed` says the steps in order. `decide_durable` refuses to guess between two pending gates.
